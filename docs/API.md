# API reference (Joseph Awaida)
All protected requests require a bearer token. Full request/response schemas are in the exported OpenAPI JSON and interactive `/docs`. Error format: `{"status":"error","message":"..."}`. Common errors: 401 missing/invalid authentication; 403 role/ownership; 404 missing resource; 409 conflicting step or workflow; 422 input validation.

## Identity integration adapter (Service 1 boundary)

### Health
`GET /Joseph-Awaida/health`

Success: 200. See Postman requests for runnable examples.

### Login
`POST /Joseph-Awaida/auth/login`

JSON body: `username, password`. Required: `username, password`.

Success: 200. See Postman requests for runnable examples.

## Service 7: Vulnerability Management

### Health
`GET /Joseph-Awaida/health`

Success: 200. See Postman requests for runnable examples.

### Create vulnerability
`POST /Joseph-Awaida/vulnerabilities`

JSON body: `title, description, cve_identifier, cvss_score, severity, asset_id, discovery_source`. Required: `title, description, cve_identifier, cvss_score, severity, asset_id, discovery_source`.

Administrator creates a vulnerability against an existing asset; queues an HTTP-delivered alert for the asset owner.

Success: 201. See Postman requests for runnable examples.

Response: VulnerabilityRecord objects with fields `title, description, cve_identifier, cvss_score, severity, asset_id, discovery_source, id, status, created_at, resolution_date`.

### List vulnerabilities
`GET /Joseph-Awaida/vulnerabilities`

Parameters: limit (query, optional), offset (query, optional)

Administrators, analysts and auditors retrieve records, with limit/offset pagination.

Success: 200. See Postman requests for runnable examples.

Response: array of VulnerabilityRecord objects with fields `title, description, cve_identifier, cvss_score, severity, asset_id, discovery_source, id, status, created_at, resolution_date`.

### Search vulnerabilities
`GET /Joseph-Awaida/vulnerabilities/search`

Parameters: cve_identifier (query, optional), severity (query, optional), asset_id (query, optional), status (query, optional)

Exact CVE, severity, asset and lifecycle status filters combine with AND. No matches return an empty array.

Success: 200. See Postman requests for runnable examples.

Response: array of VulnerabilityRecord objects with fields `title, description, cve_identifier, cvss_score, severity, asset_id, discovery_source, id, status, created_at, resolution_date`.

### Retrieve vulnerability
`GET /Joseph-Awaida/vulnerabilities/{id}`

Parameters: id (path, required)

Returns the stored vulnerability or 404. Employees are forbidden.

Success: 200. See Postman requests for runnable examples.

Response: VulnerabilityRecord objects with fields `title, description, cve_identifier, cvss_score, severity, asset_id, discovery_source, id, status, created_at, resolution_date`.

### Update vulnerability
`PUT /Joseph-Awaida/vulnerabilities/{id}`

Parameters: id (path, required)

JSON body: `description, severity, status, cvss_score`. Required: ``.

Administrator or analyst edits supported fields. Lifecycle advances one step; resolution time is generated by the server.

Success: 200. See Postman requests for runnable examples.

Response: VulnerabilityRecord objects with fields `title, description, cve_identifier, cvss_score, severity, asset_id, discovery_source, id, status, created_at, resolution_date`.

### Delete vulnerability
`DELETE /Joseph-Awaida/vulnerabilities/{id}`

Parameters: id (path, required)

Administrator only; deletion of a missing record returns 404.

Success: 200. See Postman requests for runnable examples.

Response: Message objects with fields `message`.

## Service 8: Notification and Alert Management

### Health
`GET /Joseph-Awaida/health`

Success: 200. See Postman requests for runnable examples.

### Create notification
`POST /Joseph-Awaida/notifications`

Parameters: idempotency-key (header, optional)

JSON body: `user_id, title, message, notification_type, severity`. Required: `user_id, title, message, notification_type, severity`.

Administrator or authenticated administrator service session creates a user alert. Optional Idempotency-Key prevents duplicate delivery; payload mismatch returns 409.

Success: 201. See Postman requests for runnable examples.

Response: NotificationRecord objects with fields `user_id, title, message, notification_type, severity, id, status, created_at, read_date`.

### Retrieve user notifications
`GET /Joseph-Awaida/notifications/user/{user_id}`

Parameters: user_id (path, required)

Analysts and employees may access only their own notifications. Administrators and auditors may read across users. Existing recipients with no alerts return an empty array.

Success: 200. See Postman requests for runnable examples.

Response: array of NotificationRecord objects with fields `user_id, title, message, notification_type, severity, id, status, created_at, read_date`.

### Search notifications
`GET /Joseph-Awaida/notifications/search`

Parameters: user_id (query, optional), notification_type (query, optional), severity (query, optional), status (query, optional)

Filter by user, type, severity and read status. Analysts are restricted to their own records; employees cannot search.

Success: 200. See Postman requests for runnable examples.

Response: array of NotificationRecord objects with fields `user_id, title, message, notification_type, severity, id, status, created_at, read_date`.

### Retrieve notification
`GET /Joseph-Awaida/notifications/{id}`

Parameters: id (path, required)

Returns a notification after role and ownership checks, or 404 for an invalid identifier.

Success: 200. See Postman requests for runnable examples.

Response: NotificationRecord objects with fields `user_id, title, message, notification_type, severity, id, status, created_at, read_date`.

### Delete notification
`DELETE /Joseph-Awaida/notifications/{id}`

Parameters: id (path, required)

Administrator only. Idempotency receipts remain so retries do not recreate deleted alerts.

Success: 200. See Postman requests for runnable examples.

Response: Message objects with fields `message`.

### Mark notification read
`PUT /Joseph-Awaida/notifications/{id}/read`

Parameters: id (path, required)

Administrator or owning analyst/employee marks read. Repeated calls preserve the first read timestamp. Auditors cannot mutate.

Success: 200. See Postman requests for runnable examples.

Response: NotificationRecord objects with fields `user_id, title, message, notification_type, severity, id, status, created_at, read_date`.

## Service 9: Security Playbook and Response Automation

### Health
`GET /Joseph-Awaida/health`

Success: 200. See Postman requests for runnable examples.

### List response playbooks
`GET /Joseph-Awaida/playbooks`

Administrators, analysts and auditors list available playbooks.

Success: 200. See Postman requests for runnable examples.

Response: array of PlaybookRecord objects with fields `name, description, incident_category, severity, id, created_by, created_at`.

### Create response playbook
`POST /Joseph-Awaida/playbooks`

JSON body: `name, description, incident_category, severity`. Required: `name, description, incident_category, severity`.

Administrator creates a playbook organized by incident category and severity.

Success: 201. See Postman requests for runnable examples.

Response: PlaybookRecord objects with fields `name, description, incident_category, severity, id, created_by, created_at`.

### Retrieve response playbook
`GET /Joseph-Awaida/playbooks/{id}`

Parameters: id (path, required)

Returns playbook metadata, ordered actions and append-only execution history.

Success: 200. See Postman requests for runnable examples.

Response: PlaybookDetail objects with fields `name, description, incident_category, severity, id, created_by, created_at, actions, execution_history`.

### Delete response playbook
`DELETE /Joseph-Awaida/playbooks/{id}`

Parameters: id (path, required)

Administrator deletes playbook and current actions; immutable execution history survives.

Success: 200. See Postman requests for runnable examples.

Response: Message objects with fields `message`.

### Add response action
`POST /Joseph-Awaida/playbooks/{id}/actions`

Parameters: id (path, required)

JSON body: `description, step_number, assigned_user_id`. Required: `description, step_number`.

Administrator or analyst adds a unique positive step; new steps cannot precede already started actions.

Success: 201. See Postman requests for runnable examples.

Response: ActionRecord objects with fields `description, step_number, assigned_user_id, id, playbook_id, status, completion_date`.

### Update response action status
`PUT /Joseph-Awaida/actions/{id}/status`

Parameters: id (path, required)

JSON body: `status, assigned_user_id`. Required: `status`.

Administrator or analyst advances Pending to In Progress to Completed. Requires an active qualified assignee and completed earlier steps. Completion time is server-generated.

Success: 200. See Postman requests for runnable examples.

Response: ActionRecord objects with fields `description, step_number, assigned_user_id, id, playbook_id, status, completion_date`.
