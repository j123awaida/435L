## Endpoint

```
POST http://127.0.0.1:8005/Mohammad-Nasrallah/logs
```

## Authentication

`Authorization: Bearer <token>` from Service 1, for an account whose role is **`admin`**. Service 5 rejects `analyst`, `employee` and `auditor` on this endpoint with 403, per the Service 5 authorization table in the brief.

Use a service identity with the `admin` role — the seeded local administrator works for this sprint. The acting user goes in the request body as `user_id`, not in the token, so one service account can record events performed by any user.

## Request format

```http
POST /Mohammad-Nasrallah/logs HTTP/1.1
Authorization: Bearer <admin token>
Content-Type: application/json
Idempotency-Key: incident-assignment-42

{
  "user_id": 3,
  "action": "Incident assigned",
  "description": "Incident 42 assigned to analyst 2",
  "severity": "Information",
  "related_service": "Service 3: Incident Management"
}
```

| Field | Type | Notes |
| --- | --- | --- |
| `user_id` | integer or null | Must identify an existing user. Use `null` for a system event with no identified actor, as with a failed login. |
| `action` | string | Short action name, 1–2000 characters. Searchable by substring. |
| `description` | string | What happened, 1–2000 characters. |
| `severity` | enum | `Information`, `Warning`, `Error`, `Critical`. |
| `related_service` | string | Which service produced the event, 1–200 characters. Please use your own service title so reports can group by service. |

Unknown body keys are rejected with 422. Blank required strings are rejected.

## Idempotency — this is the part that prevents duplicate events

Send an `Idempotency-Key` header with a value that is stable across retries of the *same* event. Your existing event IDs are ideal: Hassan's outbox already uses the event ID as an `Idempotency-Key` for Service 8, so reuse the same value here.

| Situation | Response |
| --- | --- |
| New key | **201** with the created record |
| Same key, same payload (a retry) | **200** with the **original** record, no second row created |
| Same key, different payload | **409** — the key is already bound to a different event |
| No key supplied | **201** every time; repeated calls create separate records |

So a retry after a timeout or a Service 5 restart is safe: it will not append a second copy. Treat **both 201 and 200 as success** and stop retrying. Retry on a connection error, a timeout, or 5xx. Do not retry on 401, 403, 409 or 422 — those need a fix, not a retry.

If Service 5 is unreachable, keep the event in your outbox and retry later rather than dropping it; the key makes a late delivery safe.

## Responses

Success returns the stored record:

```json
{
  "id": 17,
  "user_id": 3,
  "action": "Incident assigned",
  "description": "Incident 42 assigned to analyst 2",
  "severity": "Information",
  "related_service": "Service 3: Incident Management",
  "created_at": "2026-10-20T12:34:56.789012+00:00"
}
```

Errors use the project's shared shape, `{"status":"error","message":"..."}`, with an `errors` array for field validation. `401` missing or invalid token, `403` non-admin role, `409` key reused with a different payload, `422` invalid field or unknown `user_id`.

`created_at` is generated by Service 5 in UTC. There is no field for you to supply an original event time; if an event's own timestamp matters, put it in `description`.

## Do you actually need to call this?

For Sprint I, probably not — and that is intentional.

All nine services currently share one SQLite database, and `auth.audit()` already writes straight into `audit_logs`. Service 5 reads that same table, so **every event your services already record is visible through Service 5's APIs and counted in the activity report with no change on your side.** The automatic logging in `common.create_app`'s middleware and in `auth.deny` continues to work exactly as it does today.

This endpoint matters in two cases:

1. **You want an explicit audit record that the middleware does not already produce** — a domain event like "Incident assigned" rather than a generic `Data modification` row. Hassan's incident assignment is the obvious candidate.
2. **A service is deployed against a separate database** and can no longer write to `audit_logs` directly.

**Please do not do both for the same event.** If you call `POST /logs` for an action that the shared middleware already records, the event appears twice and the activity report counts it twice. Either rely on the automatic middleware record, or call this endpoint — not both. If you want a domain-specific record *instead of* the generic one, tell me and I will coordinate so only one is written.

For the same reason, `POST /logs` deliberately does **not** generate its own extra `Data modification` row: ingesting one event creates exactly one audit record.
